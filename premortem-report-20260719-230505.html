Premortem · Prospective hindsight · Jul 19, 2026

Technical Evidence Coverage Rollout

It's 6 months from now. The Phases 0–5 evidence coverage ship — capability lanes, GitHub/GitLab depth, native cloud collectors, SIEM/on-call envelopes, CrowdStrike & SentinelOne, scanner parity, migration 0100 snapshots — has failed. Here's why.

Synthesis

Most likely Failure

Unrelated regressions rode the mega-commit. An ~80–90 file mixed WIP push (evidence + Findings/Integrations/CSS) shipped breaks nobody reviewed. Green CI was treated as product safety. Customers noticed flaky pages more than new evidence value.

Most dangerous Failure

Auditor liability — evidence that lied. A lane marked covered (scanner enablement / partial sync / thin denominator) was rejected in a real SOC 2 walkthrough. Audit slipped a quarter; "honest technical evidence" became indefensible.

Hidden assumption

That mocked unit tests + a green CI suite + "connected" integration health equal auditor-defensible, production-true coverage — without live-tenant Connect/sync, scoped PRs, or collector-failure alerts.

Revised plan

  • Ship in slices, not megacommit: PR1 = GitHub/GitLab false-resolve + pagination only; PR2 = cloud collectors; PR3 = SIEM/PagerDuty envelopes; PR4 = EDR catalog+API behind a feature flag; PR5 = scanner envelopes + snapshots. Never mix Findings/CSS/UI polish into evidence PRs.
  • Live-tenant gate before GA: one real GitHub org, one GitLab (or documented Premium/Ultimate gap), one AWS Inspector account, and either CrowdStrike or SentinelOne Connect→sync→lane grade must succeed before EDR leaves "beta".
  • Never export "covered" when limitations exist: if capability_evidence.limitations contains permission_denied / unavailable_by_plan / module_not_licensed / enablement_only, grade at most limited and say so in audit-pack prose.
  • Deploy rehearsal: staging run of migration 0100 + api recreate + automatic nginx reload; documented downgrade or expand-contract path for snapshots table; retention/TTL on capability_coverage_snapshots.
  • UI copy rewrite: replace "Unknown/Stale/Not covered" + snake_case flags with plain English ("We don't have enough evidence yet" / "Evidence is older than N days" / "Needs X permission") and one clear next action.
  • Sync fairness: GitHub 429/Retry-After backoff, per-tenant job budgets, soft-fail partial pages without flipping whole-org covered.

Pre-launch checklist

  • □ Diff of the evidence ship contains only evidence-related paths (no Findings/CSS/Accounts drive-bys).
  • □ Staging: alembic 0100 upgrade + one successful Controls lane grade + audit-pack export; then deliberate api recreate and confirm no 502 without manual nginx reload.
  • □ Live sync: GitHub Security console vs Veritrail lane status match for the same org; no audit export shows covered while limitations list denials.
  • □ EDR: at least one successful CrowdStrike or SentinelOne Connect + sync on a real tenant (or feature-flagged "beta" with no audit-pack claim).
  • □ Alert: Slack/page when >N% of lanes go stale/unknown while Integrations still say connected, or when scan.collector_failed rises week-over-week.

Failure deep-dives

1 Evidence lied

The failure story

Week three after ship: cloud-castles connects GitHub. Sync paginates Dependabot/code/secret alerts until mid-page 429s. Tests only returned tidy 200/403 mocks — no rate-limit path — so partial pages graded as fresh. Secure SDLC flipped to covered. Themarquee's GitLab Premium token hit Ultimate-gated findings; collectors wrote unavailable_by_plan_or_tier but lane merge still treated enablement envelopes as enough for green. Carwiz wired CrowdStrike/SentinelOne: agents healthy, Spotlight/vuln modules 403'd; host lane still showed covered because heartbeat looked like "activity." Azure Defender stored plan tiers as enabled while assessments soft-failed on missing Reader roles.

By month four an auditor opened a Veritrail package next to the GitHub Security and Falcon consoles. Denominators and open severes did not match. Trust in "honest technical evidence" collapsed.

Underlying assumption

A green suite of mocked unit tests (403 branches included) was proof that live vendor APIs would grade the same way in production.

Early warning signs

1. First live tenant sync: lane status ≠ vendor console for the same org/repos/agents (esp. after GitHub 429s or GitLab plan gates).
2. Audit package claims covered while stored capability_evidence still lists permission_denied, unavailable_by_plan_or_tier, or EDR module-not-licensed.

2 Deploy broke production

The failure story

Tuesday 11:40pm. Phases 0–5 ship as one commit — ~80 files plus alembic 0100 — on the lone Hetzner box. Docker compose rebuilds API onto a new IP; nginx keeps the old upstream → 502s (known failure mode, usually "just reload nginx"). Migration 0100 is still creating capability_coverage_snapshots and evidence_json columns; the lock stalls; workers bounce against a half-migrated schema. Controls and audit-pack export 500. Image rollback can't undo an advanced schema. By morning snapshots fill with no retention, disk pressure climbs, and two customers are mid–SOC 2 evidence freeze with a dead product.

Underlying assumption

A solo-run, manual-migrate, single-box Compose deploy can absorb a schema-changing megacommit the same way a tiny UI tweak does.

Early warning signs

1. Redeploy recreates api and traffic 502s until manual nginx reload — still unfixed in the deploy script.
2. Migration 0100 creates append-only snapshots with no prune/TTL while grading writes on every call.

3 Unrelated regressions rode along

The failure story

Evidence coverage sat in a tree with ~89 dirty files — new EDR routes next to Findings.tsx, Integrations.tsx, checkLabels, and CSS for Accounts/Compliance/History. Shipping meant one mega-commit. Nobody read the full diff. CI failed on tsc/pydantic mocks; a fix-CI subagent greened the build without testing the Findings drawer. Production broke first on drawer wiring against half-finished control maps; next week CSS bleed made Checklist unusable. Customers filed tickets about broken pages; the evidence feature went unnoticed. Velocity collapsed into fix-CI → fix-regression loops.

Underlying assumption

Green CI on a mega-commit means the product is safe — so reviewing (or scoping) the full mixed-WIP diff is optional.

Early warning signs

1. Working tree regularly hits 50+ modified files spanning unrelated surfaces in one git status.
2. Releases show a feature commit immediately followed by a fix-CI commit with no scoped PR isolating evidence from UI WIP.

4 EDR connect failed on first real use

The failure story

Acme's security lead clicked CrowdStrike Connect in month two. Blank base URL defaulted to api.crowdstrike.com; her tenant was EU-1 → 401. She rotated secrets and scopes; founder couldn't reproduce — every CI path MagicMock'd access_token:"t". A second customer got SentinelOne verify-pass then sync death on nextCursor shape the empty pagination mock never exercised. Spotlight 403 on a no-Spotlight SKU plus a missing Hosts scope surfaced as opaque "hosts query error 403." Slack threads labeled the logos broken. By month four, prospects asked if Endpoint Security was "real."

Underlying assumption

HTTP mocks returning happy OAuth tokens and empty pagination proved Connect → sync → lane-grade would work against real CrowdStrike/SentinelOne tenants.

Early warning signs

1. Zero successful Connect/sync against a live CrowdStrike or SentinelOne tenant before GA.
2. Every EDR test patches httpx with canned 200/403 — no contract tests for regional bases, OAuth errors, or multi-page cursors.

5 Maintenance sprawl

The failure story

Month three: GitHub narrowed security-alerts OAuth scope. /user still 200'd so integration_health stayed "connected." Dependabot/code-scanning envelopes stopped updating; after 14 days lanes went stale → unknown with no pager. By month five Azure Defender empty payloads under a renamed API version, GCP SCC collector_failed rollbacks, CrowdStrike and Tenable each broke on scope/rate-limit changes. Fifteen surfaces, one founder. Month six: a design partner exported an evidence pack — half the technical lanes unknown/stale. They filed support before the founder opened a collector log.

Underlying assumption

Auth-ok connection health plus freshness windows would surface broken collectors before customers did — without deprecation monitoring or failure-rate alerts.

Early warning signs

1. Rising share of lanes in stale/unknown while Integrations still show connected.
2. Per-collector scan.collector_failed (or empty "successful" syncs) climbing week over week with no alert.

6 Auditor liability

The failure story

A customer's SOC 2 auditor probed Vulnerability Management marked covered via a scanner integration. Under the hood, scanner_capability_evidence treated any tenant activity as whole-scope assessed; a legacy GitHub path still emitted enablement_only_legacy_snapshot envelopes. The auditor found unscanned hosts / thin denominators, rejected the lane, and the audit slipped a quarter. The customer blamed Veritrail publicly. "Audit-ready evidence" became a claim the company couldn't defend.

Underlying assumption

A "covered" grade in the product UI/export is safe to hand an auditor without proving denominator completeness and non-enablement-only evidence.

Early warning signs

1. Count of single-envelope covered lanes in exported packages.
2. Presence of enablement_only / legacy_snapshot limitations inside packages that still say covered.

7 Scale & rate limits

The failure story

Prospect Northline (340 repos, ~12k Dependabot alerts) connected GitHub. The same full-pagination path built for tens of repos fired across every repo with no 429/Retry-After handling. Secondary rate-limit and abuse responses arrived; partial inventories remained; the next repo was hammered anyway. With concurrency 2 and Celery 15/20-minute caps, that job ate both workers for hours, hard-killed mid-org, and starved every other tenant's SIEM/EDR/cloud syncs. Freshness aged out; lanes flipped stale/unknown mid-demo for the CISO evaluating the product.

Underlying assumption

Full-pagination, single-job org syncs proven on tens of repos would stay fast and fair at hundreds of repos on two shared workers with no per-tenant budgets or GitHub backoff.

Early warning signs

1. Per-sync GitHub request count / wall time climbing linearly with repos × alert pages (jobs approaching the 15-minute soft limit).
2. Rising 403 secondary-rate-limit responses and queue wait for other tenants during one GitHub sync.

8 Nobody understood the UI

The failure story

The Compliance drawer shipped raw status labels — "Unknown", "Stale", "Not covered" — and limitation flags rendered as barely-humanized snake_case enums. Non-security founders read "unknown" as a Veritrail bug and "limited" as blame. Sales demos stumbled explaining phase2_native_cloud_pending provenance. Expand rates and next-action clicks stayed near zero. By month five the founder hid the Capability coverage section. Months of backend work became invisible.

Underlying assumption

Users would read coverage states as neutral technical data, not as product bugs or personal blame.

Early warning signs

1. Support tickets that treat "unknown" as a Veritrail defect.
2. Low drawer expand / action-click rates on Capability coverage vs other Fix-tab sections.
